## 0. 이 모듈이 하는 일 한 줄

**"출제 사진의 특징점 묶음"과 "방금 찍은 사진"을 받아서, 점수 하나와 판정 하나를 돌려준다.**

이 모듈은 화면도 없고 지도도 모르고 보상도 모른다. 오직 두 입력을 받아 하나의 결과를 내는 계산기다. 이렇게 잘라두면 촬영 화면(M2)과 출제 화면(M5)은 이 계산기를 호출하는 껍데기가 되고, 나중에 알고리즘을 통째로 갈아끼워도(예: ORB → SIFT) 다른 모듈은 건드릴 게 없다.

### 입출력 계약

```
입력 1: 정답 뱅크        [{keypoints, descriptors}, ...]  최대 5항목, 항목당 약 64KB
입력 2: 촬영 이미지       카메라에서 막 나온 원본
입력 3: 난이도 설정       시점차 허용치 (8/12/15%)

출력: {
  score:      0~100 최종 점수
  inliers:    검증 통과 특징점 수
  viewShift:  시점 차이 %
  bankIndex:  어느 정답과 가장 잘 맞았는지
  verdict:    인증 / 부분인증 / 근접 / 실패 / 판정불가
  elapsed:    소요 시간 (성능 측정용)
}
```

"판정불가"가 따로 있는 이유: 촬영본 자체가 흔들리거나 새까매서 특징점이 안 나오는 경우는 "틀렸다"가 아니라 "다시 찍어달라"로 안내해야 한다. 실패와 판정불가를 구분하지 않으면 사용자가 억울해진다.

## 1. 다섯 블록

```
촬영 이미지
    │
    ▼
┌─────────────┐
│ ① 정규화     │  긴 변 900px 축소 → 흑백 → CLAHE 조명 보정
└─────────────┘
    │
    ▼
┌─────────────┐
│ ② 특징 추출  │  ORB: 코너 검출 → 방향 보정 → 32바이트 기술자 × 최대 2,000개
└─────────────┘
    │                          정답 뱅크 (1~5항목)
    ▼                               │
┌─────────────────────────────────────┐
│ ③ 대조        뱅크의 각 항목과 반복:  │
│               해밍 거리 최근접 2개 →  │
│               비율 검정 0.72 통과만   │
└─────────────────────────────────────┘
    │  (뱅크 항목별 후보 짝 목록)
    ▼
┌─────────────┐
│ ④ 기하 검증  │  RANSAC 호모그래피 → 일관된 변환으로 설명되는 짝만 생존
└─────────────┘
    │  (항목별 inliers + 변환행렬 H)
    ▼
┌─────────────┐
│ ⑤ 판정      │  최고 항목 선택 → 기본점수 − 각도감점 → 4구간 판정
└─────────────┘
```

### ① 정규화 — 조건을 통일하는 블록

- **900px 축소**: 실험이 전부 이 크기 기준이라 임계값(30개, 12%)이 이 크기에서만 유효하다. 원본 해상도로 돌리면 특징점 수가 달라져 기준이 무너진다. 축소는 성능 문제이기도 하다: 4,000px 원본을 그대로 처리하면 폰에서 수십 초 걸린다.
- **흑백 변환**: ORB는 색을 안 본다. 색을 버리는 게 계절 변화(초록→갈색)에 강해지는 이유이기도 하다.
- **CLAHE(적응형 히스토그램 평활화)**: 사진을 작은 구역으로 나눠 구역마다 명암을 펴준다. 실험에서 밝기 ±35% 변화를 흡수한 게 이 블록 덕이다. 역광으로 어두운 부분과 하늘로 날아간 부분이 같이 있어도 양쪽 다 살린다.

### ② 특징 추출 — 사진을 숫자로 바꾸는 블록

ORB는 세 단계로 돌아간다.

1. **코너 검출(FAST)**: 한 픽셀 주위 원 16개를 보고 연속으로 밝거나 어두운 구간이 있으면 코너로 판정. 매우 빠르다.
2. **방향 보정**: 각 코너 주변의 밝기 무게중심으로 "이 특징점이 어느 방향을 보고 있는지"를 계산해 붙인다. 폰을 기울여 찍어도 매칭되는 이유.
3. **기술자 생성(BRIEF)**: 코너 주변에서 픽셀 쌍 256개의 밝기를 비교해 0/1 나열 → 32바이트. 이게 그 지점의 지문이다.

여기에 **8단계 피라미드**를 쓴다. 원본을 1.2배씩 줄인 8개 크기에서 각각 특징점을 뽑는다. 이 덕에 한 걸음 뒤에서 찍어(축소 0.85배) 도 매칭됐다(실험 1).

출력: 좌표 2,000개 + 기술자 2,000 × 32바이트 = 항목당 약 64KB. 정답 뱅크에 저장되는 게 정확히 이것이다.

### ③ 대조 — 짝을 찾는 블록

촬영본의 기술자 각각에 대해 정답 항목에서 가장 가까운 것 2개를 찾는다(해밍 거리 = 32바이트 중 다른 비트 수. 비트 연산이라 폰에서도 빠르다).

**비율 검정(0.72)이 품질 필터다.** 1등이 2등보다 확실히 가까울 때(거리 비율 0.72 미만)만 진짜 짝으로 인정한다. 1등과 2등이 비슷하면 "어디에나 있는 흔한 무늬"라는 뜻이라 버린다. 반복 타일 벽이 이 검정에서 대량 탈락한다.

뱅크가 여러 항목이면 **각 항목과 독립적으로 대조한다.** 겨울 도전 사진은 겨울 정답과 붙었을 때 점수가 나온다(실험 8: 봄 원본만 342개 → 겨울 정답 포함 884개).

### ④ 기하 검증 — 거짓말을 걸러내는 블록

비율 검정을 통과해도 우연히 닮은 짝이 남는다. RANSAC은 이렇게 거른다:

1. 짝 4개를 무작위로 뽑아 "이 4개가 맞다면 두 사진 사이 변환은 이것"이라는 가설(호모그래피 행렬 H)을 세운다
2. 나머지 짝 전부를 그 가설에 대입해 몇 개가 들어맞는지 센다
3. 이걸 수백 번 반복해 가장 많은 지지를 받은 가설을 채택한다
4. 그 가설에 들어맞는 짝만 생존 = **inliers**

같은 대상을 찍었으면 모든 짝이 하나의 변환으로 설명되고, 우연한 짝은 제각각이라 어떤 가설에서도 소수파다. 실험 3에서 다른 사진끼리 후보 7~9개가 검증 후 0~4개로 떨어진 게 이 블록이다.

부산물로 나오는 **변환행렬 H가 다음 블록의 입력**이다.

### ⑤ 판정 — 숫자를 결정으로 바꾸는 블록

**시점차 측정**: 원본 네 모서리를 H로 옮겨본다. 같은 각도에서 찍었으면 직사각형이 거의 유지되고, 옆에서 찍었으면 사다리꼴이 된다. 마주보는 변 길이 차이의 최대 비율 = 시점차. 실험 5에서 정답 자리 3~11% vs 한 걸음 옆 20%로 갈렸다.

**점수 합성**:

```
기본점수 = inliers 30개 → 60점, 150개 이상 → 100점, 사이 비례
각도감점 = max(0, 시점차 − 허용치) × 2  (허용치는 난이도별 8/12/15%)
최종점수 = 기본점수 − 각도감점
```

| 점수 | 판정 | 사용자에게 |
| --- | --- | --- |
| 90+ | 인증 | 보상 + 정답 뱅크 추가 후보 |
| 70~89 | 부분 인증 | 포인트 70%, "각도만 조금 달라요" |
| 40~69 | 근접 | "가까워지고 있어요" |
| <40 | 실패 | "여기가 아닌 것 같아요" |
| 특징점 <100 | 판정불가 | "사진이 흔들렸어요, 다시 찍어주세요" |

## 2. 왜 이 알고리즘인가 (대안 비교)

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **ORB (채택)** | 무료, 빠름(폰 1~2초), 특허 없음 | 극단적 시점·조명 변화에 SIFT보다 약함 | 1차 판정기 |
| SIFT | 더 강인함, 2020년 특허 만료 | ORB보다 5~10배 느림 | 현장 정확도 부족 시 교체 후보 |
| 딥러닝 임베딩 (장면 인식 모델) | 계절·날씨 변화에 가장 강함 | 모델 용량(수십 MB), 각도 구분이 오히려 어려움 | v2에서 "같은 장소" 1차 필터로 검토 |
| 클라우드 API | 구현 쉬움 | 건당 과금, 사진이 서버로 나감 | 배제 (비용·프라이버시) |

딥러닝 방식의 단점이 흥미로운데, 장면 인식 모델은 "같은 장소냐"에는 강하지만 **"같은 각도냐"에는 오히려 둔감하다.** 이 서비스는 각도가 핵심이라 기하 검증이 있는 고전 방식이 목적에 더 맞는다. 이건 심사에서 "왜 요즘 유행하는 AI 안 쓰냐"는 질문이 나오면 그대로 답이 된다.

### 확장 경로 (막히면 이 순서로)

1. ORB 파라미터 조정 (특징점 수, 피라미드 단계)
2. 판정 경계 사례만 SIFT로 재판정 (이중 판정기)
3. 딥러닝 임베딩을 "같은 장소" 1차 필터로 앞단에 추가, 기하 검증은 유지

## 3. 성능 예산 (폰 기준 목표)

| 단계 | 목표 시간 |
| --- | --- |
| OpenCV.js 최초 로딩 | 5초 이내 (최초 1회, 이후 캐시) |
| 정규화 + 특징 추출 | 1초 이내 |
| 뱅크 1항목 대조+검증 | 0.5초 이내 |
| 뱅크 5항목 전체 | 3초 이내 |
| **촬영 → 판정 표시 전체** | **5초 이내** |

5초를 넘기면 조기 종료 규칙을 쓴다: 항목 하나에서 이미 인증 기준을 넘으면 나머지 항목은 대조하지 않는다.

## 4. 검증 계획 (M1 합격 기준)

구현 후 폰 브라우저에서 직접 확인한다.

1. 실제 골목에서 같은 장면 2장 (다른 시간대) → **인증**
2. 같은 대상, 한 걸음 옆 → **각도 불일치 (부분 인증 이하)**
3. 무관한 사진 2장 → **실패**
4. 흔들린 사진 → **판정불가**
5. 전체 소요 5초 이내

이 4가지 결과와 실측 숫자로 임계값(현 가정: inliers 30, 시점차 12%)을 확정하고, 그 값을 이 문서에 갱신 기록한다.

## 5. 미결 사항

- 실측 후 임계값 확정 (4장)
- 반복 무늬 자기 유사성 검사의 기준값 — M5(출제 화면) 만들 때 실험으로 정함
- OpenCV.js 용량(~9MB)을 줄일지 여부 — 필요한 모듈만 골라 커스텀 빌드하면 3MB 수준까지 가능하나 프로토타입 단계에서는 공식 빌드 사용

## 6. 설계 보강 (2026.8.6 논의 반영)

### 기기 의존 문제 → 서버 재검증 추가

지금 구조는 폰이 스스로 채점해 결과를 보고하는 방식이라, 단말 판정만으로는 신뢰의 뿌리가 단말에 있다. 그래서 보상이 걸린 인증은 서버가 다시 확인한다(구체적 검증 절차는 비공개). 해결의 열쇠는 판정에 사진이 아니라 **64KB 특징점만 필요하다**는 사실:

- 폰은 지금처럼 즉시 판정 (사용자 경험·오프라인 유지)
- 판정 후 촬영본의 **특징점만** 서버로 전송 (사진 아님)
- 서버가 같은 계산을 재실행해 폰의 주장을 검증 (특징점 대조라 밀리초 단위)
- 쿠폰 걸린 인증은 전수 검증, 포인트만 걸린 건 표본 검증

원칙이 "판정은 단말, 서버는 공증인"에서 **"판정은 단말, 검증은 서버"**로 강화됨. 사진 원본이 안 나가는 프라이버시 이점은 유지.

기종별 카메라 차이는 전처리(축소·흑백·조명보정)가 흡수하고, 정답 뱅크에 여러 기종의 사진이 자연히 섞이는 것도 방어가 된다. 초광각 왜곡은 실측 필요 → 합격 기준에 "서로 다른 폰 2대 교차 시험" 추가.

### "비슷하다"의 애매함 → 경계의 비용을 낮추는 설계

경계를 정확히 긋는 데 승부하지 않고 경계 근처에서 틀려도 아프지 않게 설계:

1. 애매함을 각도 축 하나에 가둠 (같은 대상 여부는 실험상 중간이 빈 이분법)
2. 4구간 판정으로 경계를 절벽이 아니라 계단으로
3. 오판 방향 선택: 포인트 판정은 관대하게, 쿠폰 인증만 서버 검증으로 엄격하게
4. 경계선 위치는 현장 데이터 분포가 정함 (1단계 테스트의 목적)
5. 구조적으로 애매한 장면은 출제 단계에서 배제

### GPS 게이트 (0단계)

사진 비교 전에 출제 반경 확인. 반경 밖이면 연산 없이 차단. GPS 오차 30m 여유 포함. 탐색을 동네 안에 묶는 지역 활성화 장치이기도 함.

## 7. 구현 기록 (2026.8.6 완료)

**파일: 외계인찾기_M1_매칭엔진.html** — 단일 파일, 폰 브라우저에서 실행

구조: CONFIG(임계값 전부) / MatPool(메모리) / ImagePipeline(블록①②) / Matcher(블록③④) / Judge(블록⑤) / Gps(0단계) / Engine(오케스트레이션) / UI(DOM). Engine 이하는 DOM을 모르고 UI는 계산하지 않는다.

### 자동 시험 결과 (headless Chromium, 콘크리트 틈 사진 기준)

| 항목 | 기대 | 결과 | 수치 |
| --- | --- | --- | --- |
| 같은 자리 재촬영 | 인증 | ✅ 인증 100점 | inliers 660, 시점차 4.1% |
| 한 걸음 옆 | 부분 인증 이하 | ✅ 부분 인증 82점 | inliers 686, 시점차 20.8% |
| 무관한 사진 | 실패 | ✅ 실패 0점 | inliers 0 |
| 흔들린 사진 | 판정불가 | ✅ 판정불가 | 선명도 게이트 차단 |
| 뱅크 2장+조기종료 | 동작 | ✅ | #1에서 100점, 나머지 생략 |

전체 판정 0.2초 (데스크톱 기준. 폰은 느려도 예산 5초 내 여유).

### 시험에서 발견되어 수정한 것

**흐린 사진이 판정불가로 안 걸렸다.** 특징점 개수로 흔들림을 검출할 계획이었는데, 조명 보정(CLAHE)이 JPEG 압축 노이즈를 증폭해 심하게 흐린 사진에서도 특징점이 2,000개 나왔다. 잘못된 인증은 아니었지만(근접 68점) "다시 찍어달라"고 해야 할 사진에 점수를 준 것.

수정: **선명도 게이트 추가.** 라플라시안 분산을 CLAHE 이전의 흑백에서 측정(순서가 중요 — CLAHE 이후에 재면 같은 함정에 빠진다). 실측 분리도: 정상 사진 340~5,700 vs 심한 흐림 1.7. 기준값 40으로 넉넉히 잡음. 출제 사전 검사에도 같은 게이트 적용.

### 각도 융통성 실측 (2026.8.19 — 촬영 대상 3m 가정, 시뮬레이션)

"바라보는 각도의 융통성이 충분한가"에 대한 정량 답. 어긋남의 종류에 따라 시스템이 세 방식으로 다르게 반응한다.

**① 완전 흡수 (융통성 무제한)** — 각도로 치지 않는 어긋남:

| 어긋남 | 측정 | 판정(보통) |
| --- | --- | --- |
| 폰 기울임 45°까지 | 시점차 0.9~2.7% | 인증 100 |
| 두 걸음 앞·뒤 | 시점차 0.5~2.9% | 인증 100 |
| 거리 절반(멀리서) | 시점차 0.3% (inliers는 감소) | 인증 100 |

호모그래피가 회전·배율을 소화하기 때문. 거리는 GPS 반경이 별도로 제한한다.

**② 눈금형 융통성 (난이도 다이얼)** — 좌우(yaw)·위아래(pitch) 시점:

| 좌우 어긋남 | 환산 이동 | 느슨(15%) | 보통(12%) | 정밀(8%) |
| --- | --- | --- | --- | --- |
| 5° | 26cm | 인증 | 인증 | 인증 |
| 8° | 42cm | 인증 | 인증 | 인증 93 |
| 10° | 반 걸음(53cm) | 인증 | 인증 96 | 부분 88 |
| 12~15° | 한 걸음(64~80cm) | 인증 94~95 | 부분 88~89 | 부분 80~81 |
| 20° | 한 걸음 반 | 부분 79 | 부분 73 | 근접 65 |
| 25° | 두 걸음 반 | 근접 62 | 근접 56 | 근접 48 |

위아래: 높이차 32cm(성인 키 차이 범위)까지 인증 100, 50cm(앉기/서기)는 부분 인증. **키 차이는 문제가 안 된다.**

**③ 복합 현실 조건** — 옆 5° + 아래 4° + 기울임 6° + 한 걸음 뒤 (일상적인 재촬영 오차): 시점차 9.5% → **전 난이도 인증** (정밀 97점).

결론: "그 자리에 서긴 했다" 수준의 일상적 오차는 전부 통과하고, "옆에서 대충 찍었다"는 걸러지며, 그 사이가 절벽이 아니라 부분 인증 계단이다. 융통성의 폭 자체가 출제자가 고르는 난이도 값이고, 정답 뱅크가 쌓이면 서로 다른 위치의 정답들이 허용 원뿔을 넓혀 실효 융통성은 시간이 갈수록 커진다.

(주: 위 표는 평면 장면 시뮬레이션. 입체 깊이가 큰 장면은 같은 각도에서 시점차가 더 크게 측정되므로 실측으로 보정 필요 — 아래 현장 확인 항목과 연결)

### 조도·카메라 환경 실측 (2026.8.19)

"조도나 기종에 따라 판정이 달라지지 않는가"에 대한 정량 답. 12개 환경 조건을 시뮬레이션했다.

**매칭 자체는 전 조건에서 통과했다** (검증 특징점 466~864개, 시점차 2.5~5.6%):

| 조건 | inliers | 판정 |
| --- | --- | --- |
| 한낮 과노출 (1.7배 클리핑) | 669 | 인증 |
| 절반 그림자 | 466 | 인증 |
| 역광 (상단 날아감) | 717 | 인증 |
| 야간 (0.3배 + 노이즈) | 482 | 인증 |
| 과한 샤프닝 / 밝은 톤커브 기종 | 771 / 813 | 인증 |
| 저화질 저장 (품질 40) | 860 | 인증 |
| 화이트밸런스 왜곡 / 비네팅 | 864 / 850 | 인증 |

이유: 흑백 변환이 색·화이트밸런스를, 조명 보정(CLAHE)이 국소 명암을, 이진 기술자(밝기 비교 패턴)가 톤커브 차이를 소화한다.

**진짜 약점은 매칭이 아니라 선명도 게이트에 있었다.** 라플라시안 분산은 흐림만이 아니라 전역 밝기·대비에도 비례해서, "어둡지만 선명한" 사진(해질녘 25.3, 깊은 그늘 8.6, 안개 31.7 — 기준 40 미달)을 흐린 사진으로 오인해 판정 전에 반려했다. 매칭은 692~785개로 멀쩡히 통과하는 사진들이다.

**수정: 이중 선명도 게이트.** 밝기 불변 지표(라플라시안 분산 ÷ 밝기 분산)를 추가하고, **둘 중 하나만 통과하면 선명**으로 판정한다.

| | 절대 지표 (기준 40) | 정규화 지표 (기준 1.5) | 결과 |
| --- | --- | --- | --- |
| 어둠·안개 | 8.6~31.7 낙제 | 14.2~15.4 통과 | ✅ 구제 |
| 절반 그림자 | 65.9 통과 | 2.55 (밝기 분산 급증) | ✅ 구제 |
| 흐림 | 0.2~5.3 낙제 | 0.2~0.8 낙제 | ✅ 차단 유지 |

정규화 지표 단독으로는 그림자 사진이 오차단되어(2.55) 반드시 둘의 OR로 써야 한다. M2·M5에 적용, E2E로 어둠·안개 재촬영 "발견!" 전환과 흐림 차단 유지, 기존 회귀 전체 통과 확인. 이 과정에서 M2의 Judge가 선명도를 옛 기준으로 재검사하는 복제 분화 버그도 함께 수정했다 (버그점검 문서 5번 항목의 실증 사례).

남는 한계 (정직하게): 흐리면서 노이즈가 심한 사진은 절대 지표를 노이즈로 통과할 수 있다. 이 경우 매칭에서 실패해 잘못 인증되지는 않지만, 안내가 "다시 찍어주세요" 대신 "여기가 아닌 것 같아요"로 나간다. 실해가 없어 수용하고, 출제 쪽은 분포 검사가 별도로 막는다.

### 장면 내용 변화 실측 (2026.8.19)

"그림자나 변동 요소에 대한 융통성"의 정량 답. 조명이 아니라 **장면의 일부 자체가 바뀐** 경우다. 모든 케이스에 현실적 재촬영 오차(시점 3°, 축소, 밝기, 노이즈)를 겹쳐서 측정했다.

| 원본과 재촬영 사이의 변화 | inliers | 판정(보통) |
| --- | --- | --- |
| 또렷한 그림자가 새로 드리움 (화면 40%) | 566 | 인증 |
| 그림자 위치 이동 (원본에도 그림자 있던 경우) | 306 | 인증 |
| 주차 차량 등장 (하단 22% 가림) | 775 | 인증 |
| 현수막 부착 (글자 있는 고특징 물체 12%) | 624 | 인증 |
| 행인 2명 (기둥형 가림 15%) | 681 | 인증 |
| 바닥 젖어 반사 (하단 30%) | 721 | 인증 |
| 복합: 그림자+차량+행인 동시 | 553 | 인증 |

**한계선**: 화면을 블록 단위로 무작위 교체하며 탐색 — 50% 교체까지 인증(241개), 65%에서 무너짐(18개→실패). **장면의 절반이 바뀌어도 판정이 산다.**

원리 — 국소 특징점 투표 구조가 부분 변화에 본질적으로 강하다:
1. 판정은 "전체가 같은가"가 아니라 "충분한 수의 지점이 기하적으로 일관되게 맞는가"다. 바뀐 영역의 특징점은 **표를 못 던질 뿐, 거부권이 없다**
2. 현수막처럼 특징점이 많은 새 물체도 교란하지 못한다 — 원본에 짝이 없으니 비율 검정에서 전량 탈락
3. 그림자 경계가 만드는 가짜 경계선도 같은 이유로 무해

그 위에 시스템 층이 더 있다:
- 장기 변화(계절·개장): 정답 뱅크 누적이 흡수 (실험 8, 2.6배)
- 영구 변화(공사·철거): 임계값 자동 완화 → 휴면 전환 → 출제자 확인 (시스템_설계 2장)
- 변동 요소투성이 장면의 출제: "서로 다른 3명 성공 시 승격" 규칙이 자연 필터 — 아무도 못 푸는 문제는 승격되지 못해 보상 낭비 없이 소멸
