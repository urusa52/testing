## 0. 이 모듈이 한 일

지도에서 문제를 고른 다음, 현장으로 나서기 전에 들르는 화면이다. 여기서 사람이 하는 결정은 하나다 — **지금 이 문제를 찾으러 갈 것인가.** 그 결정에 필요한 것만 올려놓았다. 사진, 얼마나 멀리까지 가야 하는지, 얼마나 정확히 찍어야 하는지, 앞서 몇 명이 찾았는지, 출제자가 남긴 힌트.

도움을 주는 장치가 둘이다. **범위 좁히기**(반경을 절반으로 줄인다)와 **겹쳐보기**(내 사진을 출제 사진 위에 겹쳐 각도를 맞춘다). 하나는 어디로 갈지를, 하나는 도착한 뒤 각도를 도와준다. 둘 다 공짜가 아니고, 쓰기 전에 대가를 말로 알려준다.

M1 판정 엔진을 부르지 않는다. OpenCV를 안 실어서 화면이 바로 뜬다 (M2·M5는 9MB 로딩이 있다).

## 1. 파일 구조

단일 HTML 안에 여섯 덩어리가 순서대로 들어 있다. 위에서 아래로 의존하고, 아래가 위를 모른다.

```
프로토타입_M4_상세.html
├── [스타일]  디자인 토큰 (라이트/다크 두 세트) + 화면 CSS
├── [api.js]  const API = (() => { ... })()
│              ← 통합 시 이 블록을 지우고 표준 api.js를 <script src>로 붙인다
├── [Reward]  힌트 차감 계산 — 배수가 곱해지는 곳은 여기 한 군데뿐
├── [Words]   숫자 → 말 변환표 (시스템_설계 6장)
├── [Screen]  화면 상태·확인 시트·주행동
├── [Blend]   겹쳐보기 (정지 화면 blend)
└── [Dev]     개발자 모드
```

**Words를 거치지 않은 숫자는 사용자 화면에 나가지 않는다.** M2의 Stage 변환표와 같은 역할이다. 시도/성공 수, 반경, 난이도, 보상 배수가 전부 이 표를 통과한 뒤 문장이 되어 나간다. 자동 시험 2번이 이걸 검사한다.

## 2. api.js — 화면이 쓴 것과, 표준 파일에 없는 것

읽기는 `API.getQuest(id)` 하나, 쓰기는 `API.issueNonce(questId)` 하나다. 화면 코드에 `fetch`가 없다 (자동 시험 14번이 소스에서 확인한다).

내장본과 표준 파일 모두 **v1.3**이다. 아래 셋은 M4가 필요해서 생긴 것이고, 판정 후 중심 세션이 표준 api.js에 반영했다.

| 추가한 것 | 내용 | 근거 |
| --- | --- | --- |
| `CONFIG.hintPenalty` | `{ peek: 0.7, overlay: 0.5 }` | 위성 E 시작 프롬프트의 확정 계약 |
| `CONFIG.hintShrink` | `0.5` — 범위 좁히기가 반경을 줄이는 비율 | 설계 5.7 판정 3 |
| `getQuest().photo` | 출제 사진 (프로토타입은 도형 이미지 생성) | 시스템_설계 1장 Quest 표의 `photo` |

Quest에 힌트 필드는 늘지 않았다. 추가 힌트를 출제자에게 쓰게 하는 안(`hint2`)은 기각되고, 시스템이 반경을 좁혀 주는 쪽으로 정해졌기 때문이다. 덕분에 M5 출제 화면도 손대지 않는다.

`answer_gps`는 여기에도 없다. 상세 조회에도 실제 촬영 위치는 내려오지 않는다 — 개인정보 계약이 코드 형태로 유지된다.

출제 사진은 프로토타입 전용 `demoPhoto(id)`가 id를 씨앗으로 도형 SVG를 만들어 data URI로 돌려준다. 문제마다 다른 그림이 나오고, 서버가 생기면 이 함수만 실제 사진 URL로 바뀐다. 화면에는 "프로토타입 예시 이미지예요"라고 적어 두어 실제 출제 사진으로 오해할 여지를 없앴다.

## 3. 화면 규칙

### 3-1. 무엇을 보여주고 무엇을 숨겼나

| 내부 값 | 사용자 화면 | 개발자 모드 |
| --- | --- | --- |
| `stats {attempts:52, solves:4}` | "4명이 먼저 찾았어요. 헛걸음한 사람이 더 많았어요." | 그대로 |
| `radius 300 → 150` (좁힘) | 칩이 "좁힌 범위 150m 안"으로 바뀜 | 그대로 |
| `difficulty: 'precise'` | "정밀하게 · 각도까지 맞춰야 해요" | `precise` + `viewShiftTol 8%` |
| `radius: 300` | "여기서 300m 안 · 걸어서 몇 분 안이에요" | 그대로 |
| `center {36.5996, 127.2938}` | 없음 | 소수 4자리 |
| `rewardFactor 0.5` | "도움을 두 번 받았지만, 큰 쪽 하나만큼만 줄어요." | `0.5` |
| `nonce demo-7ned5gd7` | 없음 (연출만) | 그대로 |

성공률은 문장의 꼬리로만 나간다. 40% 이상이면 "찾은 사람이 꽤 많아요", 20% 이상이면 "몇 번씩 다녀간 사람도 있어요", 그 아래는 "헛걸음한 사람이 더 많았어요". 아무도 못 찾은 문제는 "첫 발견이 될 수도 있어요"로 뒤집어 말한다.

반경만은 숫자가 그대로 나간다. 위성 E 계약이 `"여기서 300m 안"`을 명시했고, 이건 출제자가 정해서 공개하기로 한 값이라 내부 상태가 아니다. 중심 세션이 이 구분(내부 상태 vs 게임의 규칙)을 설계 6장에 예외로 명시했다.

### 3-2. 도움에는 값이 있고, 값을 먼저 말한다

버튼을 누르면 바로 열리지 않는다. 확인 시트가 먼저 뜬다.

- 범위 좁히기 → "헤맬 범위를 절반으로 줄여 드려요. 대신 이번 문제의 포인트가 **조금** 줄어요" (0.7)
- 겹쳐보기 → "대신 이번 문제의 포인트가 **꽤** 줄어요" (0.5)
- 둘 다 쓴 뒤 → "도움을 두 번 받았지만, **큰 쪽 하나만큼만** 줄어요" (0.5)

조금 / 꽤가 0.7 / 0.5를 대신한다. 숫자를 안 보여주면서도 어느 쪽이 더 비싼지는 알 수 있다. 두 개를 겹쳐 써도 더 큰 쪽 하나만 적용되므로(설계 5.7 판정 2), 마지막 문장은 벌이 아니라 안심시키는 말이 된다.

브라우저 기본 `confirm()`을 쓰지 않고 시트를 직접 만들었다. 기본 대화상자는 앱처럼 안 보이고, PWA로 포장했을 때 특히 튄다.

### 3-2-1. 범위 좁히기가 하는 일

버튼을 누르면 `quest.radius`가 `CONFIG.hintShrink`(0.5)배가 되고, 반경 칩이 "좁힌 범위 150m 안 · 골목 하나 안이에요"로 바뀐다. 화면에 안내 한 줄이 붙는다 — "범위를 절반으로 줄였어요. 지도에서도 원이 작아져 있어요."

**지도는 아직 그 말을 지키지 못한다.** M3는 `quest.radius`를 그대로 그리므로, 통합 시 "이 사용자가 이 문제에서 쓴 도움"을 반영한 반경을 받아야 한다. 중심 세션이 통합 작업 ⑤로 잡아 두었다.

반경을 말로 바꾸는 `Words.radius()`는 표가 아니라 구간 판정이다. 좁히면 150·250m 같은 값이 나오는데 표로는 감당이 안 된다.

### 3-3. 겹쳐보기

확정 계약대로 **정지 화면 blend**다. 갤러리에서 고른 내 사진과 출제 사진을 같은 상자에 포개고 슬라이더로 섞는다. 라이브 카메라 오버레이는 v2이고, 여기엔 카메라 코드가 한 줄도 없다.

슬라이더를 끝까지 밀어도 출제 사진이 완전히 사라지지 않게 했다 (내 사진 100%일 때 출제 사진 50%). 완전히 사라지면 비교가 아니라 그냥 내 사진 보기가 된다.

고른 사진은 `URL.createObjectURL`로 화면에만 올라가고 어디로도 나가지 않는다. 시트에 그렇게 적어 두었다.

### 3-4. 상태별 표현 (M3와 맞춤)

| 상태 | 표현 |
| --- | --- |
| 정식 (live) | 배지 없음, 주버튼 "찾으러 가기" |
| 검증 중 (review) | 앰버 배지 "검증 중" + "세 명이 찾으면 정식 문제가 돼요" |
| 휴면 (dormant) | 배지 "쉬는 중", 주버튼 비활성 "지금은 쉬는 문제예요" |
| 내가 찾은 것 | 블루 배지 "찾음", 주버튼 "한 번 더 찾으러 가기" |

### 3-5. 개발자 모드

버전 표기 7회 탭 또는 `?dev=1`. 여기서만 좌표·임계값·난수·보상 배수가 보인다. `hintPenalty` 슬라이더 두 개가 있어 현장에서 차감 폭을 바꿔가며 문구가 어떻게 달라지는지 바로 볼 수 있다.

문제 선택 드롭다운을 달았다. M3가 아직 안 붙어 있어서 열 개 문제를 확인할 방법이 없었다. 통합 후에도 시험 도구로 남겨둘 만하다.

- 실기기에서 갤러리 사진을 골랐을 때 세로/가로 사진이 상자에 제대로 들어가는지 (`object-fit: contain`이라 잘리진 않지만 여백이 크게 남을 수 있다)

| 상황 | 지금 동작 | 이유 |
| --- | --- | --- |
| `getQuest(id)`가 없는 id로 불림 | 부팅 화면이 "이 문제를 찾을 수 없어요 / 지도에서 다시 골라 주세요"로 바뀜 | URL을 직접 고쳐 들어오는 경로가 있다 |

| `issueNonce` 실패 | "지금은 연결이 안 돼요 / 잠시 뒤에 한 번만 다시 눌러 주세요", 버튼 복구 | 주행동이 영구히 잠기지 않게 |

브라우저 저장소(localStorage)를 쓰지 않았다. 도움 사용 기록은 서버 Attempt에 남아야 할 값이라 클라이언트에 두면 어차피 우회된다.

## 6. 아직 안 한 것

- **M3 → M4 연결.** 지금은 `?id=q02`로 직접 연다. M3의 "찾으러 가기"가 이 주소로 넘겨주면 붙는다 (제안 5)
- **M4 → M2 연결.** 난수를 받고 "이제 촬영 화면으로 넘어가요"까지만 하고 멈춘다
- 도움을 여러 단계로 두는 구조. 지금은 범위 좁히기 한 번, 겹쳐보기 한 번뿐이다
- 겹쳐보기의 확대·이동. 슬라이더만 있고 사진을 키우거나 옮길 수 없다
- 출제자 표시. Quest에 출제자 필드가 없어서 "출제자가 남긴 힌트"라고만 적었다

### (원문) 중심 세션 제안

### 제안 1 · 표준 `api.js`에 `hintPenalty` 추가

M4 내장본은 v1.3으로 표기하고 `CONFIG.hintPenalty = { peek: 0.7, overlay: 0.5 }`를 넣었다. 확정 계약이지만 표준 파일(v1.2)에는 아직 없다. 표준 파일은 위성이 고치지 않으므로 그대로 두었다. 통합 시 반영이 필요하다.

### 제안 2 · 두 도움을 다 썼을 때 배수를 곱할 것인가

계약은 각각의 배수만 정했다(peek 0.7, overlay 0.5). 둘 다 쓴 경우가 정해져 있지 않아 **곱셈(0.35)**으로 구현했다. 각 도움이 독립적으로 값을 치른다는 해석이다.

- 곱셈 0.35: 도움을 겹쳐 쓰는 것을 확실히 말린다. 다만 정직하게 헤매다 결국 둘 다 쓴 사람이 3분의 1만 받게 된다
- 최솟값 0.5: "가장 큰 도움 하나만큼만 깎는다". 관대하지만 겹쳐보기를 쓴 뒤 힌트는 공짜가 된다

계산은 `Reward.factor()` 한 함수 안에 있어서 어느 쪽이든 한 줄 수정이다. 시스템_설계 원칙 4("오판 방향은 관대한 쪽으로")를 보상에도 적용한다면 최솟값 쪽이 맞을 수 있다.

### 제안 3 · Quest에 `hint2`(추가 힌트) 필드가 필요하다

"힌트 더 보기"가 열 내용이 데이터 구조에 없다. 시스템_설계 1장 Quest 표에는 `hint` 하나뿐이다. 프로토타입에서는 시드 문제 10개에 `hint2`를 임의로 채워 넣었다.

데이터 구조는 계약이므로 결정이 필요하다. 선택지는 셋이다.

1. `hint2` 한 칸 추가 (지금 구현. 가장 단순)
2. `hints[]` 배열로 바꿔 단계를 늘릴 수 있게 (M5 출제 화면에 힌트 입력칸이 하나 더 늘어난다)
3. 추가 힌트를 출제자가 아니라 시스템이 만든다 (예: 반경을 절반으로 좁혀 보여주기). 출제자 부담이 없는 대신 구현이 커진다

M5 출제 화면과 맞물리므로 거기까지 같이 봐야 한다.

### 제안 4 · UI 원칙에 "출제자가 공개하기로 한 값"이라는 예외를 명시

시스템_설계 6장은 사용자 화면에 숫자를 내보내지 않는다고 되어 있는데, 위성 E 계약은 반경 칩에 `"여기서 300m 안"`을 명시했다. 계약대로 구현했다. 둘 다 옳다고 보는데, 문서상으로는 부딪혀 보인다.

구분선은 **그 숫자가 내부 상태인가, 출제자가 정해서 공개한 규칙인가**에 있다. 판정 점수·좌표·특징점 수는 내부 상태라 숨기고, 반경은 게임의 규칙이라 보여준다. 6장 표에 한 줄 덧붙이면 다음 위성이 헷갈리지 않는다.

### 제안 5 · 화면 간 이동 규약을 정해 주기

M4는 `?id=q02`로 열린다. M3와 M2도 같은 방식이면 통합이 주소 넘기기로 끝난다. 정해야 할 것:

- M3 "찾으러 가기" → `M4?id=...` 인가, 아니면 M3에서 바로 M2로 가고 M4는 마커 탭으로만 들어가는가
- M4 "찾으러 가기" → M2로 넘길 때 난수를 누가 발급하는가. 지금은 **M4가 발급**한다 (열람 시점 기록이 M4에서 일어나므로). M2도 자체 발급 코드를 갖고 있으면 난수가 두 번 발급된다
- 단일 페이지로 합칠 것인가, 파일을 나눈 채 주소로 오갈 것인가

### 제안 6 · 힌트 사용 기록은 Attempt에 있어야 한다

지금은 메모리에만 있어서 새로고침하면 지워진다. 프로토타입이라 실손해는 없지만, 보상 배수를 서버가 계산하려면 데이터 구조에 자리가 필요하다 — 그래서 Attempt에 `hints_used`를 넣었다.

시스템_설계 1장 Attempt 표에 `hints_used` (예: `['peek','overlay']`) 한 칸을 추가하고, 보상 계산을 서버가 하도록 하면 막힌다. 난수 발급 시점에 열람 기록이 이미 서버에 남으므로, 그 기록에 힌트 사용을 덧붙이는 형태가 자연스럽다.

### 제안 7 · 현황 문서 갱신 (중심 세션 소관)

`프로젝트_현황과_계획.md`는 손대지 않았다. 반영이 필요한 것:

- 완료 목록에 M4 (`프로토타입_M4_상세.html`, 이 문서) 추가
- "다음 할 일 B" 7번에서 M4 부분 완료 표시 (M6은 위성 F로 남아 있음)
- 사용자 직접 항목에 "M4 실기기 확인 — 갤러리 사진 겹쳐보기가 세로/가로 사진에서 제대로 들어가는지" 추가
