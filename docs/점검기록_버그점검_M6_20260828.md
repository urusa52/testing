## 이번 점검의 최대 수확 — 만료된 코드가 그대로 쓰인다

**증상**: 쿠폰 코드 화면에 "코드가 만료됐어요"가 뜬 뒤에도 그 코드는 사용 처리된다. 화면을 닫아도 발급이 살아 있어 나중에 같은 코드를 쓸 수 있다.

**원인**: 만료 처리가 화면에만 있었다. `expire()`와 `close()`가 타이머를 멈추고 문구를 바꿀 뿐, 데이터 층의 발급 상태(`issued`)는 건드리지 않았고 `redeemCoupon`에도 유효시간 검사가 없었다. 즉 **유효시간이 UI의 연출이었지 규칙이 아니었다.**

이게 왜 치명인가. 이 화면은 쿠폰 사용을 확인하는 자리이고, 그 순간이 곧 과금 시점(사업계획서 5-1 ①)이다. 유효시간이 규칙이 아니면 코드를 미리 받아 두고 가게 밖에서 쓰는 길이 열린다.

**수정 3겹**:
1. 발급에 `expiresAt`을 넣고 `redeemCoupon`이 시각을 검사해 `{ok:false, reason:'expired'}` 반환
2. `invalidateCode()`를 만들어 만료·닫기 시 발급 자체를 무효화 — 코드를 미리 받아 두는 경로 차단
3. 초읽기를 마감 시각 기준으로 재계산(2번 버그와 같은 뿌리) + 화면이 다시 켜지면 즉시 재계산

프로토타입이라 시계는 이 폰의 것을 쓴다. 서버가 붙으면 이 검사는 반드시 서버 시각 기준이어야 한다(시스템_설계 5.5 ② — 폰이 주장하는 시각은 참고값). 표준 api.js로 옮길 때 함께 넘어가야 하는 조건이라 중심 세션 제안에 적었다.

## 두 번째 수확 — 초읽기가 화면 꺼짐을 못 견딘다

`setInterval`로 1초마다 `left--` 하는 방식이었다. 브라우저는 화면이 꺼지거나 앱이 뒤로 가면 인터벌을 늦추거나 멈춘다. 가게에 코드를 보여 주려고 화면을 켜 둔 채 30초만 딴 데를 봐도 남은 시간이 실제보다 크게 표시되고, 만료 처리도 그만큼 밀린다.

발급 시각에 마감 시각을 잡아 두고 매번 벽시계에서 다시 빼는 방식으로 바꿨다. 시험으로 확인한 방법: 코드를 띄운 뒤 페이지의 `Date.now`를 200초 앞으로 밀고 화면 복귀 이벤트를 던지면, 돌아오는 즉시 "시간이 지났어요"로 바뀌고 타이머가 멈춘다.

## 시험이 만든 오탐 하나 — 조건을 못 갖춘 통과

쿠폰 이름에 태그를 넣는 주입 시험이 1회차에서 '통과'로 나왔는데, 실은 그 시점에 활성 쿠폰이 하나도 남아 있지 않아(앞선 시험들이 다 써 버렸다) 검사할 대상 자체가 없었던 것이다. 같은 회차의 도감 주입 시험은 정직하게 실패했고, 두 결과가 어긋나서 발견했다.

**교훈**: 통과는 "문제가 없다"가 아니라 "이 조건에서 문제가 안 보였다"이다. 시험은 검사 대상이 실제로 존재하는지부터 확인해야 한다. 이번엔 각 시험 앞에 상태를 명시적으로 만들고, 대상이 없으면 통과가 아니라 실패로 처리하게 고쳤다.

## 중심 세션 제안 (모듈6_도감_기록.md와 중복)

1. 표준 api.js에 쿠폰 계약을 반영할 때 **`expiresAt` 검사와 `invalidateCode()`를 함께** 옮길 것. 서버 시각 기준 검증이 붙지 않으면 이번에 막은 구멍이 그대로 되살아난다.
2. `CONFIG.coupon`에 `warnDays`(만료 임박 강조 기준)를 추가했다. 표준 반영 대상.
3. 뷰포트의 핀치 확대 금지를 전 모듈에서 유지할지 재검토.
