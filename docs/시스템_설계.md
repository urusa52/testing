# 시스템 설계 — 전체 작동 원리

작성 2026년 8월 6일 · 외계인 찾기 프로젝트
기술검증_기록.md의 실험 결과를 실제 시스템 구조로 옮긴 문서다. 여기 나오는 숫자는 전부 실험에서 나온 값이고, 현장 측정 후 조정한다.

## 0. 전체 그림

```
[출제자]                      [서버]                        [탐색자]
사진 촬영                                                   지도에서 문제 선택
  │                                                           │
  ▼                                                           ▼
사전 검사 ──합격──▶ 문제 등록                            챌린지 난수 발급 ◀──
(단말에서)          '검증 중' 상태                            │
  │                    │                                      ▼
  반려 시              │                                  현장 이동 (GPS 반경)
  이유 안내            │                                      │
                       │                                      ▼
                       │                                  앱 카메라 촬영
                       │                                      │
                       │                                      ▼
                       │                              판정 (단말에서, 3단계)
                       │                                      │
                       │              ┌───────────────────────┤
                       ▼              ▼                       ▼
                  3명 성공 시     성공: 사진을            실패: 점수와
                  정식 승격       정답 뱅크에 추가         재시도 안내
                  출제 보상       보상 지급
```

원칙 세 가지.

1. **판정은 단말에서 한다.** 사진이 서버로 가지 않는다. 서버 비용 0원, 개인정보 문제 없음.
2. **서버는 심판이 아니라 공증인이다.** 난수 발급, 결과 기록, 정답 뱅크 관리만 한다.
3. **정답은 쌓인다.** 성공한 사진이 다음 도전자의 비교 기준이 된다. 시스템이 쓸수록 정확해진다.

## 1. 데이터 구조

### 문제 (Quest)

| 필드 | 내용 | 비고 |
| --- | --- | --- |
| id | 문제 번호 | |
| photo | 출제 사진 | 원본 |
| features | 출제 사진의 특징점·기술자 | 등록 시 미리 계산해 저장. 탐색자는 이것만 내려받으면 됨 |
| center, radius | 반경 중심좌표, 반경(100/300/500m) | 중심은 실제 위치가 아니라 실제 위치를 포함하는 임의 원의 중심 |
| answer_gps | 실제 촬영 위치 | 비공개. 통계·안전 검수용 |
| hint | 한 줄 힌트 | 출제자가 쓰는 것은 이것 하나뿐 (2026.8.28 확정 — 5.7 판정 3) |
| difficulty | 시점차 허용치 | 쉬움 15% / 보통 12% / 정밀 8% |
| status | 검증 중 / 정식 / 휴면 / 차단 | |
| answer_bank | 정답 사진들의 특징점 목록 (최대 5개) | 사진 원본이 아니라 특징점만 저장 |
| stats | 시도 수, 성공 수, 마지막 성공 시각 | 임계값 자동 완화의 입력 |
| solvers | 성공한 계정 목록 | 승격 판정용 |

**중요한 결정 하나: 정답 뱅크에는 사진이 아니라 특징점만 저장한다.** 특징자 하나가 32바이트, 2,000개면 문제당 약 64KB다. 사진을 저장하면 프라이버시 검토가 붙고 용량이 커지는데, 특징점만으로 판정이 되므로 사진은 버려도 된다. 성공자의 사진 원본은 본인 도감에만 남는다.

### 계정 (User)

| 필드 | 내용 |
| --- | --- |
| grade | 신규 / 일반(가입 14일 + 인증 5회) / 신뢰(출제 1개 정식 승격) |
| points, badges | 1층 보상 |
| solved[], created[] | 도감, 출제 목록 |

### 인증 시도 (Attempt)

| 필드 | 내용 |
| --- | --- |
| quest_id, user_id | |
| nonce | 서버가 발급한 일회용 난수 |
| shot_time, shot_gps | 촬영 순간 기록 — **검증 완료 후 원시 좌표는 폐기**하고 "반경 내 여부 + 출제지점과의 거리"만 보존 (개인위치정보 최소화, 2026.8.12 점검 반영) |
| hints_used | 쓴 도움 목록 `['peek','overlay']` — 난수 발급 이후 사용할 때마다 서버에 덧붙인다. **보상 배수는 서버가 이 값으로 계산한다** (2026.8.28 추가 — 5.7 판정 6) |
| result | 점수, 시점차, 사용한 정답 뱅크 항목 |

사진 자체는 올리지 않는다. 판정 결과와 메타데이터만 서버에 기록한다.
법무: 위치정보를 수집·이용하므로 정식 서비스 전 **위치기반서비스사업 신고(방통위)** 필요. 위치정보 수집 시 명시적 동의 필수.

## 2. 판정 파이프라인 (단말에서 실행)

### 전처리

1. 긴 변 900px로 축소 — 실험이 이 크기 기준. 클수록 느려지고 작을수록 특징점이 준다
2. 흑백 변환
3. 조명 보정 (CLAHE) — 흐린 날·역광 대응. 실험에서 밝기 ±35% 변화를 흡수했다

### 3단계 판정

**1단계 · 특징점 대조**

촬영본에서 ORB 특징점 최대 2,000개를 뽑고, 정답 뱅크의 각 항목과 대조한다. 비율 검정(0.72)으로 우연한 짝을 거른다.

- 뱅크에 항목이 여러 개면 **전부와 비교해서 최고 점수를 쓴다.** 실험 8: 겨울 도전 사진이 봄 원본과는 342개, 겨울 정답과는 884개 일치. 최고값을 쓰는 이유다.
- 뱅크가 5개일 때 대조 5회는 단말에서 1~2초. 허용 범위.

**2단계 · 기하 검증 (RANSAC)**

짝지어진 점들이 하나의 일관된 변환(호모그래피)으로 설명되는지 확인한다. 여기서 살아남은 개수가 "일치 특징점"이다.

- 실험 기준: 같은 자리 재촬영 400~900개, 다른 사진끼리 0~4개
- 실험은 디지털 변형이라 유리했다. 실제 기준선은 보수적으로 **30개**에서 시작하고 현장 측정 후 조정

**3단계 · 시점 차이 측정**

호모그래피로 원본 네 모서리를 옮겨 사다리꼴 찌그러짐을 잰다. 이 값이 촬영 각도 차이다.

- 실험: 정답 자리 3~11%, 한 걸음 옆 20%, 두 걸음 옆 33% 이상
- 12%를 경계로 "같은 곳 + 같은 각도"와 "같은 곳 + 다른 각도"가 갈렸다

### 점수 합성

```
기본점수 = 일치 특징점 수를 0~100으로 변환 (30개=60점, 150개 이상=100점, 사이는 비례)
각도감점 = 시점차가 허용치를 넘은 정도에 비례 (허용치 이내면 0)
최종점수 = 기본점수 − 각도감점
```

| 최종점수 | 판정 | 처리 |
| --- | --- | --- |
| 90 이상 | 완전 인증 | 전체 보상. 사진 특징점을 정답 뱅크에 추가 후보로 |
| 70~89 | 부분 인증 | 포인트 70%. "같은 곳이에요, 각도만 조금 달라요" |
| 40~69 | 근접 | 보상 없음. "가까워지고 있어요" + 재시도 |
| 40 미만 | 실패 | "여기가 아닌 것 같아요" + 재시도 |

실패 화면에서 방향을 알려주지 않는다("왼쪽으로 가세요" 같은 것). 두 가지 이유: 기술적으로 아직 연구 단계 기능이고, 게임으로서도 답을 알려주는 셈이라 탐색 재미를 깎는다. 점수 변화 자체가 뜨거워요/차가워요 역할을 한다.

### 정답 뱅크 갱신 규칙

완전 인증(90+)된 사진의 특징점만 뱅크 후보가 된다. 뱅크가 5개 차 있으면:

- 기존 항목들과 **가장 비슷한 새 항목은 버린다.** 비슷한 정답 5개보다 계절·시간대가 다른 정답 5개가 가치 있다 (실험 8의 교훈)
- 구체적으로: 새 후보와 기존 각 항목의 상호 일치도를 재서, 최고 일치도가 가장 낮은(=가장 색다른) 구성을 유지한다

### 임계값 자동 완화

```
시도 10회 이상 + 30일 무성공 → 시점차 허용치 +3%p, 특징점 기준 −5개
그 상태로 30일 더 무성공     → 한 번 더 완화
그래도 무성공                → 휴면 전환, 출제자에게 "이 장면이 아직 있나요?" 확인 요청
```

계절 변화·공사로 장면 자체가 사라진 문제를 시스템이 스스로 정리하는 장치다.

## 3. 출제 파이프라인 (단말에서 실행)

등록 버튼을 누르기 전에 세 가지 검사를 통과해야 한다.

**검사 1 · 특징점 충분한가**

특징점 400개 미만이면 반려. 실험 6에서 초점 나간 사진이 385개로 떨어졌다. 반려 문구: "이 장면은 문제로 만들기 어려워요. 더 또렷하게, 무늬가 많은 쪽으로 찍어보세요."

**검사 2 · 자기 유사성 (반복 무늬 함정)**

같은 타일이 반복되는 벽은 특징점은 많은데 어느 위치에서 찍어도 매칭된다. 검출법: 사진을 반으로 잘라 왼쪽과 오른쪽을 서로 매칭해본다. 자기들끼리 많이 일치하면 반복 무늬다. 기준 초과 시 반려: "비슷한 무늬가 반복되는 장면은 위치를 특정할 수 없어요."

**검사 3 · 안전·사생활**

- GPS가 위험 지역(하천, 철도, 공사장 폴리곤)이면 반려
- 얼굴·번호판 검출되면 반려 (온디바이스 검출 모델 사용)
- 야간 시간대 등록 시 "낮에도 찾을 수 있는 장면인가요?" 확인

통과하면 특징점을 서버에 올리고 '검증 중' 상태로 지도에 노출된다. 서로 다른 3명(출제자 제외, 신규 계정 포함)이 완전 인증하면 정식 승격 + 출제 보상. 운영자 시드 문제는 보상이 없으므로 승격 절차 없이 바로 정식.

## 4. 부정행위 방지 흐름

> 공개본 안내 — 이 장은 원문에서 요약했습니다. 각 방어가 무엇을 막고 무엇을 남기는지,
> 남은 구멍의 크기와 메우는 순서는 공개 저장소에 싣지 않습니다.

보상이 걸린 인증이라 한 겹으로 막지 않는다. 열람 시점에 서버가 일회용 난수를 발급하고,
촬영 순간의 정보를 묶어 서명한 뒤, 서버가 그 서명을 검증해야 보상이 나간다.

| 층 | 역할 |
| --- | --- |
| 앱 카메라 전용 | 현장에서 찍은 사진만 입력으로 받는다 |
| 서버 난수·서명 | 문제를 연 뒤 촬영한 것만 유효하다 |
| GPS 반경 게이트 | 사진 비교 이전에 현장 방문을 확인한다 |
| 구도 매칭 | 반경 안이어도 그 각도에 서지 않으면 통과하지 못한다 |
| 서버 재검증 | 보상이 걸린 인증을 특징점으로 다시 확인한다 |
| 신뢰 등급·교차 검증 | 다계정 자작 보상을 막는다 |

시각과 순서는 클라이언트가 주장하는 값을 믿지 않는다 — 서버가 발급한 시각과 수신한 시각
사이에 촬영이 있었는지만 본다. 도움(힌트) 사용도 서버가 기록해 보상 배수를 계산한다.

## 5. 클라이언트 구성 (프로토타입)

| 모듈 | 기술 | 상태 |
| --- | --- | --- |
| M1 매칭 엔진 | OpenCV.js (웹 빌드, ~9MB) | ✅ 자동시험 5/5 |
| M2 촬영·인증 화면 | HTML input capture → 폰 기본 카메라 | ✅ 자동시험 10/10 (api 리팩터 대기) |
| M3 지도 | Leaflet + CARTO 타일 → 카카오맵 교체 가능 구조 | ✅ 타일 실기기 확인 대기 |
| M4 문제 상세·힌트·겹쳐보기 | HTML/CSS (엔진 불필요) | ✅ 자동시험 16/16 |
| M5 출제 화면 (사전 검사 포함) | M1 재사용 | ✅ 자동시험 10/10 |
| M6 보상·도감 | HTML/CSS + 캐릭터 SVG 생성기 | ✅ 자동시험 12/12 |

프로토타입 단계에서 서버는 없다. 문제 데이터는 JSON 파일로 내장하고, 난수·서명 흐름은 화면상 연출로만 보여준다("서버 검증 중..." 표시). 판정은 진짜로 돌린다.

빌드 순서는 M1 → M2 → M5 → M3 → M4 → M6. M1이 검증되면 M2와 M5는 그 껍데기라 빠르다. 지도는 독립적이라 언제든 붙일 수 있다.

### M1 매칭 엔진의 합격 기준

- 폰 브라우저에서 사진 2장을 넣으면 10초 안에 점수·시점차·판정이 나온다
- 실제 골목에서 찍은 같은 장면 2장 → 인증
- 한 걸음 옆에서 찍은 2장 → 각도 불일치
- 무관한 2장 → 실패
- 이 결과로 기준선(현재 가정: 특징점 30개, 시점차 12%)을 확정한다

## 5.5 서버 아키텍처 검토 (2026.8.12)

### 서버가 실제로 하는 일 — 목록이 짧다

| 기능 | 성격 | 무거운가 |
| --- | --- | --- |
| 문제 목록·특징점 배포 | 정적 파일에 가까움 (문제당 ~320KB) | 아니오 — CDN 캐시 가능 |
| 난수 발급·서명 검증 | 밀리초 연산 | 아니오 |
| 특징점 재검증 | 64KB 대조, 건당 수 ms | 아니오 |
| 계정·포인트·도감 기록 | 일반 DB 읽기쓰기 | 아니오 |
| 쿠폰 발급·사용 확인 | 일반 DB + 점주 확인 화면 | 아니오 |

무거운 것(이미지 처리)을 전부 단말로 보낸 설계 덕에 서버에는 가벼운 것만 남았다. 실시간 통신도, 대용량 미디어 저장도 없다.

**부하 추산** (사업계획서 5-2 목표치 기준): 제휴 500곳 → 월 인증 37,500건 → 일 1,250건 → 평균 초당 0.014건. 주말 피크를 100배로 잡아도 초당 1.4건. **저장**: 문제 1,000개 × 뱅크 5장 × 64KB ≈ 320MB. 어느 쪽도 무료 티어 안이다.

### 스택 결정: 직접 서버 대신 BaaS (서버리스)

1인 운영에서 서버의 진짜 비용은 컴퓨팅이 아니라 **운영 부담**(보안 패치, 장애 대응, 백업)이다. 자체 VPS 대신 관리형 BaaS(Supabase 또는 Firebase)를 쓴다.

- DB·인증·서버 함수·파일 저장이 한 묶음, 무료 티어가 1~2단계 규모를 덮음
- 패치할 서버 자체가 없음. 백업 자동
- 로그인은 자체 비밀번호 시스템을 만들지 않고 카카오 OAuth — 비밀번호 유출 리스크를 원천 제거 (개인정보 점검과 일관)
- 재검증 로직(특징점 대조)은 서버 함수(Edge Function)로 — 클라이언트와 같은 OpenCV 계열 코드

### 발견된 진짜 문제 3개와 대응

**① 재검증 비결정성.** RANSAC은 무작위 표본 기반이라 같은 입력에도 실행마다 결과가 미세하게 다르고, 단말(OpenCV.js)과 서버(opencv-python)의 버전 차이도 있다. 단말은 91점, 서버는 89점이 나오면 정직한 사용자의 보상이 취소되는 사고가 난다. 대응:
- 서버 재검증은 **단말보다 관대한 기준**으로 통과 판정한다 (구체적 기준은 비공개)
- 서버 RANSAC은 시드 고정 + 반복 횟수 상향으로 분산 축소
- 목적이 부정 적발이지 재채점이 아님을 명시 — 경계 사례는 사용자 편으로

**② 시계와 순서를 클라이언트에 맡기면 안 된다.** 촬영 시각을 폰 시계로 기록하면 시계를 조작한 폰에 뚫린다. 난수 발급 시각(서버 시계)과 결과 제출 시각(서버 수신 시각) 사이에 촬영이 있었는지만 본다. 폰이 주장하는 시각은 참고값.

**③ 쿠폰 사용 확인은 점주 쪽 접점이 필요하다.** "사용 시점 과금"이 성립하려면 매장에서 쿠폰이 쓰였다는 확인이 서버에 도달해야 한다. 별도 점주 앱은 과하다. 대응: 사용자 화면에 일회용 사용 코드(큰 글씨 + 초읽기) 표시 → 점주가 자기 폰 브라우저의 점주 페이지에서 코드 입력(또는 사용자 화면의 확인 버튼을 점주가 직접 탭). 프로토타입에서는 후자로 시작.

### 프로토타입 → 서버 이행 경로

지금 프로토타입은 서버 없이 문제 데이터를 파일로 내장한다. 이행할 때 코드를 다시 쓰지 않도록, 클라이언트는 처음부터 `api.js` 한 파일을 통해서만 데이터를 읽게 만든다 (M2부터 적용). 프로토타입 단계에서 이 파일은 내장 JSON을 돌려주고, 서버가 생기면 이 파일만 fetch 호출로 바꾼다. 화면 코드는 한 줄도 안 바뀐다.

| 단계 | 데이터 출처 | 검증 |
| --- | --- | --- |
| 프로토타입 (지금) | 내장 JSON | 단말 판정만, 서버 연출 |
| 베타 (1단계 현장) | BaaS 무료 티어 | 단말 판정 + 서버 표본 재검증 |
| 정식 | BaaS 유료 전환 (월 3~5만 원 수준) | 쿠폰 전수 재검증 |

## 6. UI 원칙 — 사용자 화면과 개발자 모드의 분리 (2026.8.6 확정)

**사용자 화면에는 기능과 연출만, 숫자와 내부 상태는 개발자 모드로.**

M1 검증 페이지는 특징점 수·시점차·처리 로그·소요 시간을 전부 노출한다. 이는 검증 도구라서 그런 것이고, 사용자용 화면(M2 이후)에서는 원칙이 뒤집힌다.

| 내부 값 | 개발자 모드 표시 | 사용자 화면 표시 |
| --- | --- | --- |
| inliers 660개 | 그대로 | 표시 안 함 |
| 점수 96 | 그대로 | 외계인 등장 연출 + "발견!" |
| 시점차 20.8% | 그대로 | "같은 곳이에요, 각도만 조금 달라요" |
| 선명도 1.7 → 판정불가 | 그대로 | "사진이 흔들렸어요, 한 번만 다시!" |
| GPS 거리 412m | 그대로 | 지도에서 반경 바깥임을 색으로 |
| 보상 배수 0.5 | 그대로 | "이번 포인트는 꽤 줄어요" |
| 처리 로그 | 콘솔 패널 | 없음 |

**예외 — 출제자가 정해 공개한 규칙은 숫자로 보여준다** (2026.8.28 추가, 5.7 판정 4). 반경("여기서 300m 안")과 난이도가 여기 해당한다. 구분선은 그 숫자가 **내부 상태**인가, **게임의 규칙**인가다. 판정 점수·좌표·특징점 수·보상 배수는 내부 상태라 숨기고, 반경은 참가자가 알고 시작해야 하는 규칙이라 보여준다.

구현 방식:
- 판정 엔진의 반환값(숫자)과 화면 표현(연출)을 분리 — M1의 Engine/UI 분리 구조가 이미 이 형태라 그대로 확장
- 개발자 모드 진입: 설정 화면의 버전 번호 7회 탭 (또는 URL에 ?dev=1)
- 개발자 모드에서만: 원시 수치, 처리 로그, 임계값(CONFIG) 실시간 조정 패널, 매칭 시각화(연결선)
- 임계값 조정 패널은 현장 튜닝 도구를 겸한다 — 골목에서 값을 바꿔가며 바로 재시험

이 원칙은 신뢰에도 관련된다. 사용자에게 "82점"을 보여주면 "왜 82점이냐"는 불만이 생기지만, "각도만 조금 달라요"는 다음 행동을 알려준다. 숫자는 설명 요구를 부르고, 연출은 행동을 부른다.
