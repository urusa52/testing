## 1. 안드로이드 동작 확인

### 시험 방법

실기기가 없는 환경이라 안드로이드 크롬과 같은 엔진(Chromium)으로 Pixel 7 프로필을 에뮬레이션했다. 화면 크기·터치 입력·모바일 UA를 적용하고, 중저가 폰을 흉내 내기 위해 **CPU를 4배 감속**한 상태로 측정했다.

### 결과

| 항목 | 결과 | 판정 |
| --- | --- | --- |
| 엔진(OpenCV) 최초 로딩 | 10.4초 (CPU 4배 감속 상태) | 목표 5초 초과이나 최초 1회뿐, 허용 |
| 판정 1회 | 1.7초 | 예산 5초 내 ✅ |
| 판정 정확성 | 데스크톱과 동일 (인증 100점) | ✅ |
| 터치 입력 | 정상 | ✅ |
| 모바일 레이아웃 (393px) | 가로 스크롤 없음 | ✅ |

실기기는 이보다 빠를 가능성이 높다(감속 배율이 보수적). 그래도 로딩 화면에 "최초 1회 약 9MB" 안내가 이미 있다.

### 에뮬레이션으로 확인 불가능한 것 (현장 시험 필요)

1. **실제 카메라 호출** — `capture` 속성은 표준 동작이라 문제 가능성 낮음
2. **GPS 권한** — 주의 필요. 카톡·파일앱에서 받은 HTML을 열면 크롬이 `content://` 경로로 여는데, 이 경로는 보안 컨텍스트가 아니라서 **GPS가 차단될 수 있다.** 대비는 두 겹:
   - 이미 있는 "GPS 검사 생략" 스위치로 판정 기능 자체는 시험 가능
   - 근본 해결은 무료 호스팅(GitHub Pages 등)에 올려 https 주소로 여는 것 — M2 단계에서 적용 권장
3. 실기기 발열·메모리 — 판정당 메모리는 전량 해제 구조라 위험 낮음

## 2. 개인정보 점검

### 층 1 · 프로토타입 코드 (M1)

정적 검사 결과:

| 검사 | 결과 |
| --- | --- |
| 사진·GPS 외부 전송 | **없음** — fetch/XHR/beacon/웹소켓 호출 0건 |
| 저장 | **없음** — localStorage/쿠키 사용 0건, 모든 데이터가 세션 메모리에만 존재, 탭 닫으면 소멸 |
| 외부 접속 | OpenCV.js 내려받는 CDN 3곳뿐 (docs.opencv.org, jsdelivr, unpkg) — 코드 다운로드용, 데이터는 안 나감 |

프로토타입은 개인정보 문제 없음. "사진이 단말 밖으로 나가지 않는다"가 코드 수준에서 사실로 확인됨.

### 층 2 · 지원서와 프로젝트 문서

- **지원서에 쓰던 사진 한 장에 주차 차량이 식별 가능한 수준으로 담겨 있었다.** 자동차 번호는 개인정보로 취급될 수 있어 해당 사진은 교체하기로 했다. 새로 찍는 사진도 같은 기준(번호판·얼굴·문패 배제)으로 촬영한다
- 프로젝트 문서 7종 전수 검색: 이름·이메일·전화번호 등 연락처 정보 **없음**

### 층 3 · 서비스 설계 (앞으로 지켜야 할 것)

**법적으로 가장 중요한 발견: 위치정보법.** 이 서비스는 사용자의 위치정보를 수집·이용하는 사업이라, 정식 서비스 전에 **위치기반서비스사업 신고(방송통신위원회)**가 필요하다. 신고제라 진입장벽은 낮지만 누락하면 처벌 대상. 사업계획서 실행 계획에 법무 체크리스트로 추가할 것. 위치정보 수집 시 **명시적 동의**도 법정 요건.

**설계 수정 1건 — 인증 시도 기록의 GPS.** 시스템_설계.md의 Attempt 구조가 `shot_gps`(촬영 순간 원시 좌표)를 서버에 기록하게 되어 있다. 계정에 연결된 위치 이력은 민감한 개인위치정보다. 수정: **서버 검증이 끝나면 원시 좌표는 폐기하고 "반경 내 여부 + 출제지점과의 거리"만 남긴다.** 판정·통계에 필요한 건 그것뿐이다.

기존 설계에서 이미 잘 되어 있는 것:
- 인증 사진은 서버로 안 감 (특징점만 전송, 특징점으로 원본 복원은 제한적)
- 정답 뱅크에 사진 대신 특징점만 저장
- 출제 시 얼굴·번호판 자동 반려 (검출 모델은 v2, 그 전까지 시드 문제는 수동 확인)
- 사유지·주거지 촬영 금지 규칙

베타 공개 전 필요한 문서: 개인정보처리방침, 위치정보 이용약관.
